    Web Hacking Toolkit: Burp Suite + the tools that matter

    You do not need fifty tools. You need Burp Suite set up correctly, a handful of command-line workhorses, and a workflow you repeat until it is muscle memory. This page gets you from zero to intercepting traffic in about twenty minutes.

    1. Burp Suite

    Burp Suite is the standard toolkit for testing web applications. It sits between your browser and the lab server as an intercepting proxy, so you can see every request, pause it, change it, and replay it. Nearly every one of the 201 lab challenges is solved with some part of Burp.

    Community vs Pro

    Burp Suite Community Edition is FREE, and it is enough for all 201 lab challenges. The paid Pro version adds faster scanning and unthrottled Intruder attacks, but nothing in this lab requires it. One honest limitation: Community Edition throttles Intruder (it inserts a small delay between requests), so automated attacks run slower. For the lab's small payload lists this is only mildly annoying, never a blocker. Keep your lists short and focused.

    Download

    Get Burp Suite Community Edition from the official PortSwigger download page:

    Download Burp Suite Community Edition

    Install

    • Windows: run the downloaded installer and follow the wizard. Burp appears in your Start menu.
    • macOS: open the downloaded DMG and drag Burp Suite into Applications.
    • Linux: make the installer executable and run it: 
      chmod +x burpsuite_community_linux*.sh
./burpsuite_community_linux*.sh

    Burp needs a 64-bit operating system and a Java runtime. The bundled installers handle Java for you in almost all cases.

    First launch

    1. Open Burp Suite. Choose Temporary project (no need to save anything yet).
    2. Choose Use Burp defaults for the configuration. The defaults are correct for this lab.
    3. Burp starts with a proxy listener on 127.0.0.1:8080. That is the address your browser will talk to in the next section.

    Burp needs the lab running. Start PenTrix VulnLab first (see the Install guide), then start Burp, then point your browser through the proxy. That order avoids most first-run confusion.

    2. Proxy setup

    Burp only sees traffic that your browser sends through it. You have two ways to route traffic: a manual browser proxy setting (simple, always works) or FoxyProxy (recommended, one click to switch on and off).

    Option A: manual proxy (any browser)

    1. Open your browser's network or proxy settings.
    2. Set the HTTP proxy to 127.0.0.1 and the port to 8080. Enable the proxy for all protocols (HTTP and HTTPS).
    3. Remove localhost and 127.0.0.1 from the proxy bypass or exceptions list. Browsers often skip the proxy for localhost by default, which means Burp sees nothing.

    Option B: FoxyProxy (recommended)

    1. Install the FoxyProxy browser extension from your browser's add-on store.
    2. Add a new proxy: type HTTP, host 127.0.0.1, port 8080.
    3. Set the URL pattern to *://localhost:3000/* (or add a pattern that matches the lab's URL) so only lab traffic goes through Burp and the rest of your browsing stays direct.
    4. Toggle the extension on when you practice, off when you are done. One click, no settings to revert.

    Skip the Burp CA certificate. That cert is only for intercepting HTTPS traffic. This lab is plain HTTP on localhost, so there is nothing to decrypt. Skip that step entirely for this lab.

    Scope: keep Burp focused on the lab

    Pointing your whole browser through Burp floods the history with noise from other tabs. Add the lab to Burp's target scope:

    1. Go to the Target tab, then the Scope sub-tab.
    2. Add http://localhost:3000 to the scope (include rule: host localhost, port 3000).
    3. Tick Use advanced scope control where available, so out-of-scope traffic stays out of your history and your site map.

    Quick check that everything works: with the proxy on, visit the lab. Requests should appear in Proxy > HTTP history. (Certificate warnings on other, HTTPS tabs are normal: you skipped the CA on purpose, so toggle the proxy off when you leave the lab.)

    3. Core workflow

    Nearly every challenge follows the same rhythm: intercept a request, replay it, change one thing, observe what changes in the response. You do not need to master all of Burp. You need four core features, plus two bonus helpers at the end, and the habit of repeating this loop until it feels natural.

    Proxy: your window into the traffic

    The Proxy sits between your browser and the lab server. Every request passes through it, and you can hold, inspect, forward, or drop each one.

    • Intercept on/off: in the Proxy tab, open the Intercept sub-tab. The toggle decides whether requests pause in front of you. With intercept on, each request waits for you to act. With it off, traffic flows straight through but is still logged.
    • Forward vs Drop: when a request is paused, Forward sends it to the server exactly as you see it (edit it first if you like). Drop throws it away and the browser sees the request fail.
    • HTTP history: the log of everything, every request, every response, status codes, methods, parameters. When you wonder what you actually sent, the answer is here.

    Typical lab use: keep intercept off most of the time so browsing feels normal, then find the interesting request in HTTP history.

    Repeater: your workbench

    Repeater is where nearly every challenge gets solved. It takes one request and resends it again and again, changing one thing at a time.

    1. In HTTP history, right-click any request and choose Send to Repeater (shortcut: Ctrl+R).
    2. Switch to the Repeater tab. Your request is now in its own numbered tab.
    3. Edit anything: the method, the path, a header, or a value in the body.
    4. Click Send. The response appears on the right.
    5. Change one more thing, click Send again, and compare the two responses.

    The power of Repeater is iteration speed: twenty variations in a minute, watching exactly how the server reacts. Every tab keeps its own send and response history for comparison.

    Intruder: automated repetition

    Intruder does in Repeater's job automatically: it repeats a request with different values in chosen positions.

    1. Right-click a request and choose Send to Intruder (shortcut: Ctrl+I).
    2. In Positions, the attack type is Sniper (the default, and the one you want here). Select a value, click Add §; it now sits between two § symbols.
    3. In Payloads, use simple lists: numbers (1, 2, 3) or short word lists you type or paste.
    4. Click Start attack. The results table shows one row per payload with response length and status code.

    Remember the Community throttle: attacks run slower than in Pro, so keep payload lists short and focused.

    Decoder: reading and writing encodings

    Servers and browsers constantly encode text (URL encoding, Base64, HTML entities). Decoder translates between encoded and readable forms. Paste text in, pick a transform (Decode as URL, Decode as Base64, Decode as HTML, or the matching Encode as versions), and chain transforms by stacking them. If a response contains a blob that looks like random characters, try Decoder before assuming it is meaningless.

    Comparer: spot the difference (bonus)

    When two responses look identical but the server behaves differently, Comparer finds the exact difference. Send two requests or responses to Comparer (right-click, Send to Comparer), select both items, and click Compare by words. The highlight shows which bytes changed. Typical lab use: change one value, compare the two responses, and the differing field is often the clue.

    Logger: the full story (bonus)

    Logger is the always-on record of everything Burp sees, Proxy traffic included, with powerful filtering. When you need to reconstruct what you did in the last ten minutes, Logger has the story. Make sure Proxy and platform traffic logging are switched on in Logger settings so the record exists when you need it.

    Worked mini-example: intercepting a login (mechanics only)

    This example uses no real challenge route, no flags, and no payloads. It is only about the mechanics: intercept, replay, modify, observe.

    1. In Burp, go to Proxy > Intercept and toggle intercept on.
    2. In your proxied browser, open the lab and submit the login form with any values you like (for example a test username and a test password).
    3. Burp now holds the request. You will see a POST to the login path, with the username and password visible in the body. Nothing has reached the server yet.
    4. Click Forward. The request goes to the server and the browser shows the login result.
    5. Open Proxy > HTTP history and find that POST (it is the most recent POST to the login path).
    6. Right-click it and choose Send to Repeater (or press Ctrl+R).
    7. In Repeater, change the username value to something else (another plain username, nothing special).
    8. Click Send and read the response on the right.
    9. Change the username to a third value, click Send again, and compare the two responses. Notice what changed and what stayed the same.

    That loop, intercept, find in history, send to Repeater, change one thing, send, compare responses, is the entire Burp workflow for this lab. Every challenge is a variation of it.

    Troubleshooting

    • Port 8080 already in use when starting Burp. Another program (another Burp instance, a local server, Docker) is already listening on 8080. Fix: in Burp go to Proxy > Proxy settings (the gear icon in the Proxy tab), edit the listener on 127.0.0.1:8080 and change the port to 8081, then update your browser proxy config (or FoxyProxy) to 127.0.0.1:8081 so both sides match.
    • HTTPS sites outside the lab show certificate errors. You skipped the CA install on purpose (the lab is plain HTTP, so you do not need it). Fix: that is expected. Just toggle the proxy off (FoxyProxy one click) when you browse outside the lab.
    • Localhost traffic not appearing in Burp. The browser is bypassing the proxy for localhost (many do this by default). Fix: remove localhost and 127.0.0.1 from the proxy bypass or exceptions list. In FoxyProxy, check the URL pattern covers the lab's URL instead of excluding it.
    • Burp feels slow, pages hang halfway through loading. Intercept is on and holding a request waiting for you. Fix: look at the Intercept tab. If a request is waiting, click Forward (or Drop), then turn intercept off if you do not need to pause traffic right now.
    • Proxy configured but the browser ignores it. Firefox and Chrome/Edge handle proxy settings differently. Fix: Firefox has its own proxy settings and its own certificate store, configure both inside Firefox (Settings > Network Settings for the proxy, Settings > Privacy & Security > Certificates for the CA). Chrome and Edge use the operating system's proxy and certificate settings, so configure them at OS level (or use FoxyProxy in either browser to keep things simple).
    • Burp will not start at all. Incompatible Java runtime or a non-executable installer on Linux. Fix: Burp needs a 64-bit operating system and a compatible Java runtime (the bundled installer usually handles this). On Linux, if you downloaded the .sh installer, make it executable first (chmod +x burpsuite_community_linux*.sh), then run it. If it still fails, run it from a terminal so you can read the actual error message.

    4. Other tools

    Burp is your daily driver. These seven command-line tools cover the jobs Burp does slowly or not at all: scanning, fuzzing paths, testing SQL injection, cracking hashes, forging tokens, and mapping the network. Each entry shows the install plus the two to four commands you will actually use.

    OWASP ZAP

    A free, open-source web scanner and a solid second proxy. Useful when you want an automated spider and active scan of the lab, or a free alternative to Burp for a second opinion.

    # Debian/Ubuntu (check your distro's package name, or download from zaproxy.org)
sudo apt install zaproxy
# Launch the GUI
zaproxy
# Headless quick scan of the lab
zap.sh -cmd -quickurl http://localhost:3000 -quickprogress

    Download and docs: zaproxy.org

    sqlmap

    Automates detection and exploitation of SQL injection once you have found a suspicious parameter with Burp. Point it at a URL or at a saved Burp request.

    # Debian/Ubuntu
sudo apt install sqlmap
# Test a parameter for injection (harmless detection first)
sqlmap -u "http://localhost:3000/search?q=test" --batch
# List databases once injection is confirmed
sqlmap -u "http://localhost:3000/search?q=test" --dbs --batch
# Replay an exact Burp request you saved to a file
sqlmap -r request.txt --batch

    ffuf

    A fast web fuzzer. Its main job in the lab: discovering hidden paths, files, and parameters by trying thousands of words quickly.

    # Debian/Ubuntu
sudo apt install ffuf
# Fuzz for hidden paths on the lab
ffuf -u http://localhost:3000/FUZZ -w /usr/share/wordlists/dirb/common.txt
# Same, but only show 200 and 403 responses, follow redirects
ffuf -u http://localhost:3000/FUZZ -w /usr/share/wordlists/dirb/common.txt -mc 200,403 -r

    gobuster

    Another directory and DNS brute-forcer, written in Go and very fast. If ffuf feels fiddly, gobuster's simpler flags are a friendly alternative.

    # Debian/Ubuntu
sudo apt install gobuster
# Directory brute-force on the lab
gobuster dir -u http://localhost:3000 -w /usr/share/wordlists/dirb/common.txt
# DNS subdomain brute-force (recon phase)
gobuster dns -d example.com -w /usr/share/wordlists/dirb/common.txt

    nmap

    The network mapper. In this lab its job is small but important: confirm what is listening locally and check service versions before you start.

    # Debian/Ubuntu
sudo apt install nmap
# What is open on the lab host, with service versions and safe scripts
nmap -sV -sC localhost
# Fast full-port sweep of the lab host
nmap -p- --min-rate 1000 localhost

    hashcat

    Cracks hashes with wordlists and rules, using your GPU for speed. In the lab it fits the crypto module (md5-crack) and auth brute-forcing jobs.

    # Debian/Ubuntu
sudo apt install hashcat
# Crack MD5 hashes with rockyou.txt
hashcat -m 0 hashes.txt /usr/share/wordlists/rockyou.txt

    Docs: hashcat.net/wiki

    Node with jsonwebtoken

    A scriptable way to forge and inspect JSON Web Tokens. In the lab it fits the jwt module: craft a token by hand, then send it from Repeater.

    # Install the library
npm install jsonwebtoken
# Decode a token and read its payload
node -e "console.log(require('jsonwebtoken').decode(process.argv[1]))" "eyJhbGciOi...token..."

    Library: jsonwebtoken on npm

    Honorable mentions

    • Nikto: quick web-server misconfiguration scan (nikto -h http://localhost:3000). Noisy but fast.
    • dirsearch: another path brute-forcer with smart recursion and good defaults (dirsearch -u http://localhost:3000).
    • wfuzz: the classic parameter and path fuzzer (wfuzz -c -w wordlist.txt --hc 404 http://localhost:3000/FUZZ).
    • Sublist3r / amass: subdomain enumeration for the recon phase (sublist3r -d example.com). Mostly useful beyond localhost, but good to know the names.

    Wordlists live at /usr/share/wordlists/ on Kali and Debian-based systems. For bigger lists, install SecLists (sudo apt install seclists).

    5. What not to reach for

    Raw curl one-liners as your default. They still work, and you will use curl plenty. But if every challenge is a curl command you pasted together by trial and error, you are training your memory, not your understanding. Do it in Repeater first, where you can see the full request and the full response side by side. Graduate to curl when you know exactly what you are sending and why.

    Raw sockets. Nothing in this lab needs them. If you are writing socket code to talk to this lab, you have wandered off the path. Come back to Repeater.

    6. Honest limits

    • Burp Community's Intruder is throttled. It is slow on purpose. For this lab that is fine, the guessable spaces are small. If you find yourself waiting an hour on an attack, the approach is wrong, not the tool.
    • No tool here replaces understanding the vulnerability. sqlmap can extract a database, but it cannot tell you why the query was injectable. If you cannot explain the bug in one sentence, you have not finished the challenge, even with the flag in hand.
    • The best tool in this lab is still your own attention. Read the responses. All of them. The app tells you more than you think.

    7. Tool-to-module mapping

    When you know the vulnerability class, you know the tool. Use this table to pick the right weapon before you start clicking.

    • SQLi: sqlmap, Burp Repeater
    • XSS: Burp Proxy, Burp Repeater, Burp Decoder
    • IDOR: Burp Repeater, Burp Comparer
    • Auth (login, sessions, brute force): Burp Proxy, Burp Repeater, Burp Intruder (Sniper)
    • SSRF: Burp Repeater
    • File upload: Burp Proxy, Burp Repeater
    • JWT: Burp Decoder, Burp Repeater
    • LFI: Burp Repeater, ffuf
    • Command injection: Burp Repeater
    • CSRF: Burp Proxy
    • XXE: Burp Repeater, Burp Decoder
    • Crypto: Burp Decoder
    • Race conditions: Burp Intruder (Sniper, single-packet style)
    • Directory discovery: ffuf, gobuster, dirsearch
    • Recon: nmap, Nikto, Sublist3r, amass

    The pattern is simple: Burp Repeater appears almost everywhere because most challenges are won by crafting and replaying HTTP requests by hand. The CLI tools are specialists you call in for their one job.

    8. Bug hunting methodology

    Tools without a method are just noise. Every challenge, from the easiest to the nastiest kill chain, follows the same five phases in the same order:

    1. Recon: learn what you are looking at. Map open ports with nmap, note the tech stack from headers and error pages, and enumerate subdomains and paths where relevant. Do not attack yet. Understand first.
    2. Mapping: click through the application with Burp's proxy on and intercept off. Build the site map: every page, every form, every parameter, every API endpoint. Write down where user input goes in and where output comes out.
    3. Testing: pick one input point and one vulnerability class from the mapping table above. Send it to Repeater, change one thing at a time, and watch the responses. Narrow and deep beats wide and shallow: finish testing one parameter before moving to the next.
    4. Exploiting: once a test shows strange behavior, turn it into a reliable exploit. Confirm it twice, then capture the flag the way the challenge asks (most award automatically; beacon challenges need the token sent back, see the Docs page).
    5. Documenting: write down what you did while it is fresh: the vulnerable request, the exact change that worked, and why. This becomes your break-then-fix patch notes and your future cheat sheet.

    Order of operations matters. Recon before mapping, mapping before testing, testing before exploiting. Skipping ahead to exploitation with no map is the number one reason beginners get stuck: they fuzz blindly instead of understanding the one request that matters.

    When you are stuck, go back one phase. Stuck exploiting? Your testing was too shallow. Stuck testing? Your map is incomplete. The answer is almost always in the previous step, not in a new tool.
